# RUSTSEC-2024-0370 investigation

Status: unresolved upstream maintenance advisory; no patch, ignore, version override, or dependency change applied. Checked on 2026-10-20 (America/New_York) against KREYNIMA commit `16aa2d7` and the published registry/upstream sources linked below.

## What introduces it

The [RustSec record](https://github.com/RustSec/advisory-db/blob/main/crates/proc-macro-error/RUSTSEC-2024-0370.md) classifies `proc-macro-error` as `informational = "unmaintained"`, with no patched versions. The affected locked version is 1.0.4.

Two introducing crates were confirmed with `cargo tree --locked --manifest-path apps/desktop/src-tauri/Cargo.toml --target all -i proc-macro-error`:

```text
kreynima-desktop
└── tauri 2.12.4
    ├── gtk 0.18.2
    │   ├── gtk3-macros 0.18.2 ── proc-macro-error 1.0.4
    │   └── glib 0.18.5 ── glib-macros 0.18.5 ── proc-macro-error 1.0.4
    └── tauri-runtime-wry 2.12.2
        ├── tao 0.37.1 ── gtk 0.18.2 (same branches)
        └── wry 0.57.0 ── gtk/webkit2gtk (same branches)
```

Other GTK consumers include Tauri's `muda` menu dependency and related GLib libraries. Fixing just one macro crate would leave the other introduction. This diagram is a relevant-path summary, not the complete dependency graph.

The Tauri/Wry GTK dependencies are conditioned on Linux/BSD targets. Separate inverse-tree checks for `x86_64-pc-windows-msvc`, `aarch64-apple-darwin`, and `x86_64-apple-darwin` returned “nothing to print.” The full-graph check still sees the affected package because Cargo.lock records dependencies for multiple platforms. These tree checks are not native compilation or GUI tests for untested architectures.

Adding a direct dependency does not replace transitive requirements; a rename or unverified Cargo patch is not a supported fix. Registry/repository checks found recent releases and non-archived repositories for [manyhow 0.14.1](https://github.com/ModProg/manyhow) (released 2026-10-13) and [proc-macro2-diagnostics 0.11.0](https://github.com/SergioBenitez/proc-macro2-diagnostics) (released 2026-09-26). These are actively published upstream migration candidates, not compatible application-level replacements; this investigation does not certify their security or perform the consumer migrations. The upstream [Tauri tracking issue #10910](https://github.com/tauri-apps/tauri/issues/10910) remains open at review time.

## Actual risk and limits

This advisory reports lack of maintenance, not a specific memory-safety flaw or a demonstrated execution vulnerability. The affected library is consumed by procedural macros during compilation of the GTK stack; this investigation found no Windows/macOS runtime path to it in the resolved target trees. It does not demonstrate an MCP remote-execution capability.

Unmaintained build dependencies can leave future defects unfixed and increase supply-chain/review risk on build hosts that use them. A locked version improves reproducibility but is not a security remediation. Absence from these target trees does not prove complete application security or eliminate other dependencies' risks. Linux native builds remain separately blocked by missing system libraries in the current workspace.

## Recommended resolution

Prefer a published, supported Tauri/runtime/Wry/WebKit/GTK stack that adopts the newer macro stack, or a supported upstream backport on both affected 0.18 macro branches. Track Tauri #10910 and relevant releases; verify published dependency constraints rather than following a development branch or assuming a new top-level release fixes the graph.

When a compatible release exists, update the smallest supported set of dependencies and the lockfile, rerun all-target inverse trees and the full Rust advisory/license/source checks, then Windows/macOS compilation, JavaScript/MCP tests, and native smoke tests. For any continued Linux support, validate that platform with its system prerequisites as well.

Until then, retain the failing advisory check and keep the issue as an explicit acceptance gate. Any proposed scoped risk acceptance must be a separate documented maintainer decision; this investigation does not grant it. Do not silently ignore the advisory, force GTK 0.19 into `^0.18` consumers, vendor an unaudited fork, or disable required toolkit features simply to obtain a green check.
